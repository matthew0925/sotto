# そっと（Sotto）技術仕様書（開発者ハンドオフ用）

対象：性暴力予防・安全確保のためのパーソナルセーフティアプリ
方針：同意記録機能は搭載しない／安全確保（SOS・見守り・相談導線・記録）に特化

---

## 1. プロダクト概要

| 項目 | 内容 |
|---|---|
| アプリ名 | そっと（Sotto） |
| タグライン | 帰るまでが、いちばん大事。 |
| 解決する問題 | 危険を感じた瞬間、誰にも気づかれず／複雑な操作なしに助けを呼べない |
| コアUX | ①長押しで緊急電話画面 ②帰宅チェックイン（タイムアウト通知） ③端末内のみの記録 ④相談窓口への即時導線 |
| 非搭載機能 | 同意の事前記録・電子署名（法的効力なし、誤った安心感のリスクがあるため） |

---

## 2. MVPスコープ

### 含める
- 長押しで緊急電話画面（誤操作防止のホールド式）→ iOSの発信確認
- 帰宅チェックイン（タイマー・タイムアウト通知から、登録連絡先へのSMS作成画面＋位置情報リンク）
- 相談窓口ディレクトリ（#8891、#8008、110、地域窓口。オフラインキャッシュ）
- 端末内暗号化ジャーナル（クラウド同期なし）
- アカウント登録不要（電話番号・氏名・メール収集をしない）

### 含めない（v1では）
- 音声解析による危険検知（誤検知リスク・常時録音のプライバシー問題が大きいため要検証）
- SNSログイン・ソーシャル機能
- サーバーサイドでのユーザーデータ保存
- 同意記録・電子署名機能

## 3. アーキテクチャ概要

```
┌─────────────────────────────┐
│         クライアントのみ           │
│  (iOS App / Android App)     │
│                               │
│  - ローカル暗号化DB (Journal)  │
│  - Keychain / Keystore        │
│    (連絡先・設定の保存)         │
│  - バックグラウンドタイマー       │
│  - ネイティブSMS/Tel Intent    │
│  - 位置情報 (発信時のみ取得)     │
└─────────────────────────────┘
        │ (サーバー通信は最小限)
        ▼
┌─────────────────────────────┐
│  相談窓口データ (静的JSONを     │
│  アプリに同梱＋年1-2回更新配信)  │
└─────────────────────────────┘
```

**設計原則：サーバーを持たない、または持っても「ユーザーデータを一切保存しない」構成にする。**
これは開発・運用コストを下げるだけでなく、「クラウドにデータを保存したくない」という
既存アプリへの不満（レビュー調査より）への直接的な回答になる。

## 4. iOS 実装（Swift / SwiftUI）

| 機能 | 実装方法 | 留意点 |
|---|---|---|
| 長押しSOS | `LongPressGesture` + `DragGesture(minimumDistance:0)` で押下中の経過時間を計測 | 誤操作防止のため最小1.2〜1.5秒。`UIImpactFeedbackGenerator`で振動フィードバック |
| 電話発信 | `UIApplication.shared.open(URL(string:"tel://8891")!)` | Info.plistに`LSApplicationQueriesSchemes`は不要（telは標準） |
| SMS送信 | `MFMessageComposeViewController`（アプリ内で確認画面を出す） | **iOSはバックグラウンドからの無確認自動送信を許可しない**。タイムアウト時は通知を出し、ユーザーがワンタップで送信確定する設計にする（後述） |
| チェックインタイマー | ローカル通知（`UNUserNotificationCenter`） | バックグラウンド実行時間に依存せず、期限時刻の通知をOSへ事前登録する |
| 位置情報 | `CLLocationManager`、`when-in-use`権限のみ要求 | 常時位置情報権限（Always）はApple審査で厳しく問われるため、SOS発火時のみ取得する設計を推奨 |
| 暗号化ジャーナル | `Core Data` + `NSFileProtectionComplete` もしくは `SQLCipher` | 端末ロック時は復号不可にする（`NSFileProtectionComplete`が簡便） |
| 連絡先の保存 | `Keychain Services`（`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`） | 端末再起動後の初回ロック解除以降はロック中のショートカットから取得可能。iCloudキーチェーン同期はオフ |

### iOSでの重要な制約
通常のiOSアプリは、`MFMessageComposeViewController`を使って確認なしにSMSを送信できません。
標準導線は「期限通知＋SMS作成画面」で、利用者が送信を確定します。任意機能として、利用者自身が
Apple純正「ショートカット」でパーソナルオートメーションを作成した場合に限り、App Intentから
「送信が必要」・宛先・本文を渡して自動送信を構成できます。同じ見守りIDの送信情報は、
重複送信を防ぐため最初の取得時に1回だけ渡します。ショートカット側の送信成功はアプリから確認できないため、
取得後にショートカットが失敗した場合も自動再送はしません。アプリからオートメーションや実行時刻を自動作成・変更することはできません。

## 5. Android 実装（Kotlin）

| 機能 | 実装方法 | 留意点 |
|---|---|---|
| 長押しSOS | `GestureDetector` + カスタムView、`CountDownTimer`で進捗表示 | `VibrationEffect`で触覚フィードバック |
| 電話発信 | `Intent(Intent.ACTION_CALL)` | `CALL_PHONE`権限が必要（審査で用途説明が必須） |
| SMS自動送信 | `SmsManager.sendTextMessage()` | `SEND_SMS`権限。**Androidは条件次第でバックグラウンド無確認送信が可能**だが、Google Playの「機密権限」ポリシー上、デフォルトSMSアプリでない場合は制限されることがあるため要事前確認 |
| チェックインタイマー | `WorkManager`（`OneTimeWorkRequest` + `setInitialDelay`）＋ `Foreground Service`（タイマー中は通知常駐） | Doze/App Standbyでの遅延に注意。Foreground Serviceの通知タイプは`location`を明示 |
| 位置情報 | `FusedLocationProviderClient`、`ACCESS_FINE_LOCATION`は発火時のみ要求 | バックグラウンド位置情報権限は原則使わない設計に |
| 暗号化ジャーナル | `Room` + `SQLCipher for Android` | パスコード/生体認証（`BiometricPrompt`）でジャーナルにロックをかける |
| 連絡先の保存 | `EncryptedSharedPreferences`（Jetpack Security） | — |

## 6. プライバシー・データ設計

1. **収集しない**：氏名、メールアドレス、アカウント、行動ログ
2. **端末外に出さない**：ジャーナルの内容、チェックインの相手情報
3. **一時的にのみ使う**：位置情報（SOS発火時・チェックインタイムアウト時のみ取得し、送信メッセージに含めたら破棄）
4. **バックアップの扱い**：iCloud/Google Driveへの自動バックアップ対象からジャーナルDBを除外（`NSURLIsExcludedFromBackupKey` / Android `android:allowBackup="false"`もしくは`fullBackupContent`で除外指定）
5. **削除**：設定画面から「すべてのデータをこの端末から削除」をワンタップで用意（DV加害者等に端末を確認された場合の安全確保にも直結する）

## 7. App Store / Google Play 審査上の注意点

- **カテゴリ**：Medical/Health ではなく Utilities または Lifestyle が妥当。緊急通報アプリとして誤解されないよう説明文で明確化（110番の代替ではないことを明記）
- **CALL_PHONE / SEND_SMS 権限の説明**：Google Playは機密権限（SMS・通話ログ）の使用目的を審査時に個別説明する必要がある。「個人の安全確保のための緊急連絡機能」であることを具体的に説明する動画・スクリーンショットの準備が必要
- **偽装アイコン機能（電卓に見せかける等）は非推奨**：一部の類似アプリで採用例があるが、Appleはアプリの実際の機能を偽装するUIを審査で問題視する可能性が高い。安全性よりリジェクトリスクが上回るためv1では見送り
- **医療・法律アドバイスと誤認されない文言**：「診断」「証拠として有効」等の断定表現は避ける

## 8. 開発体制・工数目安（個人開発）

| フェーズ | 内容 | 目安期間 |
|---|---|---|

## 9. 未確定事項（支援団体への相談で解消したい点）

- チェックインのメッセージ文言は当事者を怖がらせない表現になっているか
- 「記録」機能の名称・説明が、被害を前提とした押しつけがましい印象を与えていないか
- 地域窓口データの一覧は内閣府データを定期的に同期する仕組みが必要（手動更新だと陳腐化する）
- 誤発報・いたずら利用への対策（東京都のワンストップ支援センターでも「目的外利用と判断される相談には対応できない場合がある」と明記されている）
